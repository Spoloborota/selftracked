## Scope: the only door history comes through

Every other write verb refuses what the schema forbids of a *new* record —
open statuses only, real commit ranges, ascending contiguous worklog, a live
file behind every link. Historical records satisfy none of that, and the
design answer is not to weaken the verbs but to give history a single, marked
door: `import --legacy`. S9 builds that door and nothing else writes through
it.

The deliverable is one verb with a batch reader in front of the existing write
paths, plus a date-derivation engine that is the stage's real substance —

- **`import --file F [--format md-table|json] [--legacy]`.** Batch creation of
  tasks, epics, stories, and worklog rows from one source file. The two
  formats are `md-table` (the shape the bootstrap inventory and ledger are
  written in — this is what S10 imports) and `json`. Without `--legacy` it is
  an ordinary batch of *new* records and every verb rule binds. `--legacy`
  turns on three relaxations and nothing more (INV-259, INV-439): synthesized
  timestamps (events-marked), `commits='legacy: …'` accepted by R6/close, and
  terminal states insertable **on the INSERT path** — the transition matrices
  gate `UPDATE` only, so a direct insert of DONE/CLOSED is not a matrix
  violation (INV-442).

- **The date-derivation engine (the substance).** Per worklog row, the date is
  taken from the best primary source, git first (INV-260): (1) the newest
  resolvable cited commit's git **author** date — author over committer so a
  rebase cannot rewrite worklog chronology; "newest" so a multi-commit or
  `a..b` citation dates the increment by its *finish*; else (2) the row's
  explicit `date` field; else (3) the import time. Git outranks the explicit
  field deliberately — narrative-contaminated dates are the §5 drift class and
  imported narratives carry it. When (1) and (2) both exist and disagree on the
  **calendar day (UTC)**, the importer warns, git wins, and both values are
  recorded (INV-261) — the modal contamination is an adjacent-day midnight
  drift a "more than N days" threshold would sleep through, so the recorded
  disagreement is the audit trail, not a correction.

- **Two honest bounds on dates the engine cannot derive** (amendment
  `import-date-bounds`, already accepted, INV-548/INV-549): a date **later than
  the import moment is refused** (a future date is provably not an event date —
  the documented failure is a session crossing midnight writing tomorrow's date
  all day), and a date **earlier than the earliest commit touching the source
  file is reported, not refused** (an older record can legitimately be
  transcribed into a new file, but the broken bound is stated). Neither
  computes a date; they only reject or flag impossible ones.

- **Token handling in the commits cell.** A non-sha placeholder (prose like
  "see commit", template leftovers) resolves nothing and falls through to
  `commits='legacy: …'` (INV-262); an unresolvable *sha-shaped* token (a typo)
  is left verbatim so R5 flags it in full `verify` — rewriting it to `legacy:`
  would mask the typo. (The verbatim-typo half is spec §6.2 text; no S9 row
  isolates it. **Correction at close:** this open first claimed the typo half was
  "covered by the placeholder-fallthrough fixture's negative arm" — it was NOT
  (that fixture cites prose, not a sha-shaped typo), a claim the S9 critic round
  caught. The typo path now has its own end-to-end evidence,
  `internal/cli/testdata/import-typo.txtar`: a sha-shaped unresolvable token is
  stored verbatim and `verify` reports a red R5.)

- **The per-epic source map (deterministic).** One `import` events row per
  epic carries a compact per-worklog-row date-source map — one short
  `seq:source` code per row in worklog seq order (INV-264, INV-447) — so date
  provenance is auditable without a per-row events row. It is **deterministic**:
  two imports of the same file byte-agree (INV-264). A flat batch-time stamp in
  place of the map is **forbidden** (INV-265) — real chronology recoverable
  from git must not be flattened into one synthetic epoch.

- **Importer structural obligations**, enforced by reusing the existing write
  paths so the schema gates fire: worklog rows appended in ascending per-epic
  order so the contiguity trigger sees them in order (INV-269, INV-443); ledger
  rows bundling several increments split into one worklog row per increment
  (INV-444); a story materialized for every referenced S-id, V-rows exempt
  (INV-270, INV-445); one `import` events row per terminal entity so R12
  matches per entity and a single batch-summary row is rejected (INV-446); one
  path-dictionary row per (class, scope) (INV-438); future-increment rows homed
  to their epic, not `park`ed (INV-448); non-file pointers degraded to note
  content (INV-451); owner steers with no BLOCKED story landing as notes, no
  unblock event synthesized (INV-452).

- **The date-regime disclosures**, verified by fixture on real imported rows:
  imported rows' `date` means "when the increment finished (best primary
  approximation)" while live rows mean "when recorded" — one column, two
  regimes read uniformly downstream (INV-268); task rows have no commits cell so
  task dates come only from explicit fields or import time — task-level
  narrative-date contamination is out of git-first's reach in v0 (INV-267); and
  the best-effort honesty caveat — plain rebases preserve author dates but
  squash-merges rewrite them, so recovered dates are primary-source
  approximations (INV-266).

The stage closes on the plan's DoD (§4 line 206): a synthetic legacy corpus
round-trips → `verify` green → golden dump; the date-priority matrix including
the calendar-day warn; the source-map determinism fixture.

## Reuse, not reinvention

The importer is a reader in front of machinery that already exists. It does not
open a second write path: it calls the same row-insertion the verbs use, so the
contiguity trigger (INV-269/443), the terminal-INSERT allowance (INV-442), the
per-entity events rows (INV-446), and R6/R12 all bind exactly as they do for
live writes — `--legacy` only relaxes the three named inputs, never the gates.
Git is invoked read-only for author-date resolution through the same
`exec.CommandContext(ctx, "git", …)` shape `stale` and the R11 hook-checks use;
no new dependency. The dump/`verify` round-trip that closes the stage is the
S5/S7/S8 machinery unchanged — S9 adds rows through the front door and asserts
the back door still reads them out identically.

## Close appendix (2026-07-21)

The importer lives in `internal/verb/import{,_dates,_insert,_mdtable}.go`, with
`internal/verb/import_test.go` and the CLI fixtures
`internal/cli/testdata/import{,-typo}.txtar`. Implementation and its first
critic-driven fixes are commit `acdd980`; `make gates` exits 0 there (interim
evidence, D-EP8).

**The review (spec §5).** Five fresh adversarial critics ran in parallel,
read-only and sandboxed, under distinct lenses — spec-fidelity, code-correctness,
data/semantics, test-design, security/privacy — then, after fixes, one
verification re-critic on the fixed artifact. The full adjudication (every
finding, my verdict, the evidence) is
`docs/research/2026-07-21-s9-import-critic-round.md`.

**Confirmed clean by hand.** No command injection (the `shaShape` gate and the
`--` pathspec separator are airtight; `exec.Command` runs no shell) and no
privacy leak (the only address is `importer@test.invalid`, RFC 2606; no
hostnames, absolute paths, secrets, or non-English prose in the new files).

**Accepted and fixed.** Commit-cell classification (a `legacy:` value or prose
can no longer masquerade as a citation to skip the `--legacy` gate or pollute
R5); the DUPLICATE-task `task_links` pairing and `dup_of` validation that R7
needs; the §8.1 control-char gate extended over `epic_criteria`; the INV-549
lower bound taken as the MIN over git-log (topological, not author-date sorted);
a deterministic `epics.created_at` that never postdates `close_sweep`;
clean-refusal (not a raw driver error) when re-importing an existing story, epic,
or path; every imported task events-marked so a backfilled date is never a hidden
forgery; and every silent md-table malformation turned into a loud refusal. Test
strengthening added the typo-verbatim/R5 path, the INV-446 negative
counter-example, per-relaxation without-`--legacy` refusals, and the literal
`legacy:` assertion.

**Refuted (refute-by-default).** The two date bounds are git-exempt by design
(`import-date-bounds`); the corpus is trusted operator input, so "marker
spoofing via note" carries no privilege boundary; `future_increment` meets
INV-448 (homed-not-parked) and is now a real gate (it must name an epic); the
delimiter set and empty-corpus no-op are format choices; a subprocess timeout /
git-lookup cache is a parked perf note, not a correctness defect.

**One self-correction.** My first cut of the explicit-date fix (A5) refused *any*
non-git date without `--legacy`, which pre-decided the escalated E1 question in
the restrictive direction and broke plain batch-creation of tasks; the
re-critic (RC-1) caught it. The shipped behavior admits an explicit date without
`--legacy` (only a synthesized import-time date needs it) and marks every
imported task — closing the forgery concern by *marking*, not by refusal.

**Escalated to the owner (post-review, non-blocking).** E1 — does an explicit
date field require `--legacy` (§6.2's relaxation list says no; INV-056's wording
could be read as yes)? E2 — a calendar-day disagreement is recorded in the
worklog `note`, not encoded in the machine-findable source map; is that
sufficient for "both values recorded"? E3 — md-table cannot express a bundled
increment, so INV-444's split is exercised only through JSON; flag for the S10
ledger corpus.
