## Notable realizations

- **R4 is not yet in `internal/rules`.** The DB-only engine has r6–r9,
  r12; R4 is pure-SQL and belongs with them for `--fast`. It is added at
  S7 as a sibling function, but NOT into `DBOnly` — that set is `load`'s
  contract (§8.5), closed at S4 as exactly R6–R9/R12. `verify` and
  `--fast` call `DBOnly` + R4; `load` keeps calling `DBOnly` alone.
- **A spec-text seam, refuted, no action.** §8.5 line 918 calls load's
  set "the DB-only rule set of §7 `--fast` (R6–R9, R12)" — omitting R4 —
  while §7 and INV-289 put R4 in `--fast`. Read precisely these describe
  two different call sites: `load` runs R6–R9/R12 (its own concern, a
  malformed correction in a loaded dump is caught by the post-load full
  `verify`), and `verify --fast` runs the superset with R4. Not a defect;
  recorded so the next reader does not re-derive it. S4/§8.5 scope is
  closed and untouched.
- **Advisory vs red is the exit contract.** R1–R9 and R12 are red
  (violations → non-zero exit); R10, R11, R13, R15 are advisory (reported,
  exit unaffected). The reporting layer must separate the two and the
  exit code must follow only the red set — asserted by fixture.
- **R5 and R11 read git/hooks state**, so their fixtures run inside real
  git repos (testscript supports this); R11's textual matcher additionally
  gets direct table-driven Go tests because end-to-end cannot cheaply
  enumerate its spellings and its two must-NOT-match comment cases.

## What this open did not do

No code was written. Close-review seams to watch: (1) R1 check 2's
"loaded in-memory, re-dumps byte-equally" must reuse the §8.5 loader path
(not a second, divergent parser) or it tests the wrong thing; (2) the
advisory/red split must be visible in both output grouping AND exit code,
not one or the other; (3) R11's after-`#` comment stripping is the rule's
documented failure surface — the commented-out must-NOT-match cases are
load-bearing, not decorative; (4) `verify` opens the DB read-only (it must
never heal or write) — the one exception the spec grants is none, so any
write path in verify is a defect.
