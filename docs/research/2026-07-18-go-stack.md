# Go stack for selftracked v0 — evidence-based, version-pinned proposal

Date: 2026-07-18. Status: research result for owner review. Every version
below was verified against official sources (go.dev, pkg.go.dev, GitHub
releases) on this date; nothing is quoted from memory. Scope: the spec's §3
(architecture), §6 (CLI), §16 (quality gates) drive the requirements — a
single static Go binary (`selftracked`, alias `strk`), pure-Go SQLite via
`modernc.org/sqlite` (CGO_ENABLED=0), ~24 fixed verbs with `--json` and a
strict 0/1/2 exit-code contract, a hand-rolled deterministic SQL dump
serializer that is also the security boundary (fuzzed), agents as the primary
caller.

---

## 1. Go toolchain

**Facts (verified 2026-07-18):**

- Current stable: **Go 1.26**, released **2026-02-10**; latest point release
  **go1.26.5** (2026-07-07). Previous line: go1.25.12 (2026-07-07).
  Source: <https://go.dev/doc/devel/release>
- Cadence: major release every six months, February/August; **Go 1.27 is
  expected ~August 2026** (weeks away). Each major release is supported until
  two newer majors exist. Source: <https://go.dev/wiki/Go-Release-Cycle>
- **Corrected after round-5 verification:** Go 1.26 originally shipped a
  `go mod init` default that wrote the previous line (`go 1.25.0`) "to
  encourage compatibility with supported versions", but that default was
  **reverted in go1.26.1** (golang/go#77653, accepted; #77860, backported;
  closed 2026-03-04) — a current go1.26.x `go mod init` writes the current
  version. This fact no longer supports any floor rationale below; it is
  recorded here only so the reversal is legible to a future reader.
  Source: <https://go.dev/doc/go1.26>, golang/go#77653, golang/go#77860

**Verdict — toolchain policy:**

- `go.mod`: `go 1.25.0` — note the `go` directive is both a language version
  and a *minimum-toolchain* requirement, not only a "language floor". The
  floor stands on two facts, not on `go mod init`'s default (see the
  corrected note above — that default no longer supports anything): (i) the
  official support policy — each major release is supported until two newer
  majors exist, so 1.25 remains supported through 1.27's release — and (ii)
  the driver `modernc.org/sqlite` v1.54.0's own go.mod declares `go 1.25.0`,
  so the floor cannot go lower without dropping the pinned driver version —
  plus **`toolchain go1.26.5`**. Semantics caveat
  (<https://go.dev/doc/toolchain>): under the default `GOTOOLCHAIN=auto` the
  `toolchain` directive only *upgrades*, never downgrades — a machine whose
  installed default is newer than go1.26.5 builds with that newer toolchain.
  The directive is a floor-raiser; the true exact pin is the environment
  setting **`GOTOOLCHAIN=go1.26.5`**, set in CI and in the Makefile, so every
  developer and CI runner builds with the identical toolchain regardless of
  what is installed locally.
- CI builds the module twice: once with the pinned toolchain, once with the
  latest current−1 point release (`GOTOOLCHAIN=go1.25.12`) so the declared
  minimum is honest, not aspirational.
- Bump ritual: when Go 1.27 lands (~2026-08), move `toolchain` to 1.27.x
  after its first point release proves quiet, and raise the `go` directive to
  1.26.0. Point releases (1.26.6 …) are adopted immediately — they are
  security fixes.

**Language features to mandate** (all within the 1.25 floor; enforced by
`go fix -diff` and golangci-lint rather than prose — see §2, §3):

- `any` over `interface{}`; `min`/`max`/`clear` builtins (1.21).
- `slices`/`maps`/`cmp` stdlib over hand-rolled loops (1.21).
- Range-over-int `for i := range n` (1.22).
- **Range-over-func iterators** (`iter.Seq`, `iter.Seq2`, 1.23) — the natural
  shape for the dump serializer (rows in PK order per table) and for verify
  rules streaming over entities; also `strings.SplitSeq`/`FieldsSeq` (1.24).
- Generic type aliases (1.24) where they clarify, not as decoration.
- `go.mod` **`tool` directive** (1.24) for pinning Go-tool dependencies
  (govulncheck — §9) instead of a `tools.go` blank-import file.
- `os.Root` (1.24) for filesystem operations confined to the repo root —
  directly relevant: artifact resolution, `paths move`, `init` seeding all
  operate strictly on repo-relative paths, and `os.Root` makes escapes a
  runtime error instead of a code-review hope.
- `testing.B.Loop`, `t.Context()` (1.24); `testing/synctest` (1.25) if any
  timing-dependent code appears (busy-timeout retry paths).
- 1.26-only APIs (`errors.AsType`, `new(expr)`, `bytes.Buffer.Peek`,
  `T.ArtifactDir`) are **deferred until the floor rises to 1.26** — using
  them today would falsify the `go 1.25.0` claim.

## 2. The `modernize` analyzer → `go fix` (state changed in 2026)

**Facts:**

- Historically `modernize` lived at
  `golang.org/x/tools/gopls/internal/analysis/modernize` with a standalone
  runner. That page still exists (x/tools gopls v0.23.0, 2026-07-07).
  Source: <https://pkg.go.dev/golang.org/x/tools/gopls/internal/analysis/modernize>
- **As of Go 1.26 the modernizers moved into the toolchain proper**: "`go
  fix` … completely rewritten as the home of Go's 'modernizers'", including a
  source-level inliner driven by `//go:fix inline`.
  Source: <https://go.dev/doc/go1.26> ("Go command" section).
- Empirically verified on go1.26.x: `go tool fix help` lists dozens of
  registered fixers (no official count is published; the registered set also
  includes non-modernizer fixers) — among them `any`, `rangeint`,
  `stringsseq`, `stditerators`, `minmax`, `mapsloop`, `slicescontains`,
  `slicessort`, `stringsbuilder`, `stringscut(prefix)`, `waitgroup`,
  `testingcontext`, `forvar`, `fmtappendf`, `reflecttypefor`, `omitzero`,
  `newexpr`, `inline` — and `go fix -diff ./...` prints a unified diff of
  the pending rewrites. Official sources (go.dev/doc/go1.26,
  go.dev/blog/gofix) document no exit-code contract for `-diff`; the blog's
  recommended CI pattern is "fail the build if the diff is non-empty", i.e.
  the pipeline keys on the *output*. **Corrected after round-5 verification:**
  empirically, on go1.26.4, `go fix -diff` DOES exit 1 on a non-empty diff
  and 0 on an empty one — verified, but this exit-code behavior is nowhere
  in the official docs, so it is not a contract Go promises to keep across
  releases; output emptiness is the actually-documented signal. The gate
  design therefore checks **both**: exit status (fails fast on the verified
  behavior) and output emptiness (the documented, load-bearing check).

**Verdict:** do not wire the old gopls-internal runner. CI runs
`go fix -diff ./...` and fails on a non-zero exit status *or* non-empty
output (exit status is verified-but-undocumented so output emptiness stays
load-bearing; checking both also catches a tool error that exits non-zero
with empty stdout); locally `make fix` checks and `go fix ./...`
applies. The
gopls v0.23.0 analyzer remains what the editor shows — same fixes, no extra
pin needed. This *is* the mechanical enforcement for §1's "mandated modern
features".

## 3. golangci-lint

**Facts:**

- Current release: **v2.12.2** (2026-05-06); v2.12.0 2026-05-01, v2.11.x
  Mar 2026. Source: <https://github.com/golangci/golangci-lint/releases>
- The v2 config format (`version: "2"`) is mandatory: linters are selected
  via `linters.default: none|standard|all|fast` plus `enable`/`disable`
  lists; formatters (gofumpt etc.) moved to a separate top-level
  `formatters` section; v1 configs do not load.
  Source: <https://golangci-lint.run/docs/configuration/file/>

- Chosen policy for this project (a private parent project's lint config was
  consulted during drafting): the maximal posture, `linters.default: all`,
  with each disabled linter carrying a one-line justification.
  - **`default: all` + per-linter disables, never wholesale** — the disable
    list *is* the policy document; every entry states why.
  - **depguard in `list-mode: strict`** as a ratified import allowlist:
    strict is the mode that actually enforces an allowlist (lax mode only
    flags explicitly denied imports). For selftracked the allowlist is
    tiny: `$gostd`, own module, `modernc.org/sqlite`. This mechanically
    enforces the "no accidental dependency" posture.
  - **gosec tuned, not disabled**: perm thresholds set to the tool's
    intended 0o755/0o644; G204/G304 excluded *with prose* — a local CLI's
    whole job is opening caller-given paths and exec'ing a fixed tool set,
    which is exactly the pattern `criteria check` (deliberate shell
    execution) and artifact resolution require.
  - **Test-file exclusions** for funlen/gocognit (table-driven fixtures) and
    forcetypeassert (a wrong assert panicking *is* the test signal).
  - **gofumpt with `module-path` set** so golangci's bundled gofumpt groups
    own-module imports identically to the standalone binary.
  - Planned disables, each with rationale: `exhaustruct` (fights zero-value
    idiom), `ireturn`, `lll` (gofumpt owns format), `cyclop`+`gocyclo`
    (duplicate metric; keep `gocognit`), `noinlineerr` (bans the idiomatic
    inline-err form; its autofix is known to produce uncompilable rewrites
    in some codebases).
  - Deliberately kept **ON** despite being commonly disabled elsewhere:
    `err113`/`wrapcheck` — selftracked's exit-code mapper (§6.1 of the
    spec) is *built on* `errors.As`/sentinel discrimination of driver
    errors, so error-identity linters pull their weight here. Likewise
    `gochecknoglobals`/`paralleltest`: decide on measured evidence, not
    convention.

**Verdict:** golangci-lint **v2.12.2**, v2 config, `linters.default: all`
with a short, reasoned disable list (start from the choices above);
formatters: gofumpt. Linters that matter most for this specific tool:
`exhaustive` (closed status vocabularies → every switch over a status enum
must be total), `errorlint`, `sqlclosecheck`, `rowserrcheck`, `depguard`
(strict allowlist), `gosec` (tuned), `gocritic`, `revive`, `misspell`,
`unparam`, `copyloopvar`/`intrange` (overlap with `go fix` is harmless).
Install via the official script into `./bin` (the project explicitly warns
against `go install` builds of the linter); pin the version in the Makefile.

## 4. CLI framework

**Facts (all verified on pkg.go.dev, 2026-07-18):**

| Candidate | Version | Published | Notes |
|---|---|---|---|
| spf13/cobra | v1.10.2 | 2025-12-04 (corrected after round-5 verification: GitHub API timestamp, UTC) | Maintained (5 releases in 2025: v1.9.0, v1.9.1, v1.10.0, v1.10.1, v1.10.2); pulls pflag + mousetrap; POSIX-flag + completion machinery |
| urfave/cli v3 | v3.10.1 | 2026-06-28 | Active (monthly releases through 2026); zero runtime deps; v3 stable |
| alecthomas/kong | v1.16.0 | 2026-07-15 | Active; declarative struct-tag model; small dep tree |
| stdlib `flag` + dispatch | go1.26.5 | — | Zero deps; total control |

Sources: <https://pkg.go.dev/github.com/spf13/cobra?tab=versions>,
<https://pkg.go.dev/github.com/urfave/cli/v3>,
<https://pkg.go.dev/github.com/alecthomas/kong?tab=versions>

**Fit analysis against the spec:** the verb set is **closed (~24 verbs, two
levels deep at most)** and frozen by the spec; the primary caller is an
agent, so what matters is: byte-deterministic error output
(`{"error":{"code","message"}}` on stdout as JSON), the exact 0/1/2 exit-code
contract, and refusal messages that name the fix. Framework "wins" —
completion, help theming, plugin-style command registration, config binding —
are dead weight here, and every framework has opinions that must be fought:
cobra prints usage text on errors and routes through its own exit paths
unless silenced flag-by-flag (`SilenceUsage`, `SilenceErrors`,
`SetFlagErrorFunc`…); urfave/cli and kong both own `main`'s error path and
default usage rendering. A misparse must produce exit 2 with a JSON error
object, not a framework's usage dump.

**Verdict: stdlib `flag` + a small hand-rolled verb registry.** One
`internal/cli` package: a `map[string]Verb` (verb → func(ctx, args) →
(result, error)), one `flag.FlagSet` per verb with `ContinueOnError` and
discarded output, one place that renders success/error JSON and maps errors
to exit codes. This is ~150 lines that would otherwise be spent configuring
a framework into silence, with zero dependencies to audit under §8.5's
security posture. Runner-up if hand-rolling is vetoed: **kong v1.16.0**
(declarative, small, active; its struct model doubles as documentation of the
closed verb set). Cobra is disqualified on error-path control and dependency
weight, not maintenance; urfave/cli v3 is fine but adds nothing stdlib
doesn't for a fixed verb set. The `strk` alias is an install-time
symlink/hardlink (and a second `builds.binary` entry under goreleaser later)
— never a second main.

## 5. Configuration

**Facts:** the spec is explicit (§9): "No config file: configuration is
`meta` rows edited via `config`." Remaining knobs: per-verb flags (`--json`,
`--force`, `--quiet`…) and one environment variable read by the *hook shell
script*, not by Go (`SELFTRACKED_SKIP`). Current library versions, for the
record: koanf **v2.3.5** (2026-05-30,
<https://pkg.go.dev/github.com/knadh/koanf/v2>); viper is cobra-adjacent and
file-oriented.

**Verdict: no config library.** stdlib `flag` + `os.Getenv` (if a Go-side
env knob ever appears, e.g. `SELFTRACKED_DB` for tests). koanf/viper would
import a file-merging, hot-reloading machine to read zero files; both fail
the depguard allowlist test trivially. Precedence, if a conflict ever
exists: flag > env > `meta` row — documented in one paragraph, not a
library.

## 6. Database layer

**Facts:**

- Driver: `modernc.org/sqlite` **v1.54.0** (2026-07-15), wrapping SQLite
  **3.53.3**, BSD-3. Its go.mod requires `go 1.25.0` and pins
  **`modernc.org/libc v1.74.1`**; the package docs mandate using *exactly*
  the libc version from the driver's own go.mod (fragile-dependency notice,
  cznic/sqlite issue #177). Spec §3.1's floor (≥ v1.48.2 for the RETURNING-
  via-Exec fix) is satisfied with headroom.
  Sources: <https://pkg.go.dev/modernc.org/sqlite>,
  <https://gitlab.com/cznic/sqlite/-/raw/v1.54.0/go.mod>
- sqlc: **v1.31.1** (2026-04-22). SQLite engine state today: STRICT-table
  parsing landed in v1.18 (issue #1877, closed, milestone 1.18.0); sqlc has
  used modernc.org/sqlite internally since v1.25; v1.31.0 added a database
  analyzer (via ncruces/go-sqlite3) and `SELECT *`/`RETURNING *` expansion
  for SQLite. Generated code targets `database/sql`, so it is
  driver-agnostic — it *works* with modernc.
  Sources: <https://github.com/sqlc-dev/sqlc/releases>,
  <https://github.com/sqlc-dev/sqlc/issues/1877>
- sqlx: maintenance-mode reflection scanner; adds struct-tag scanning only.

**Verdict: hand-written repository layer over `database/sql`. No sqlc, no
sqlx.** Rationale, in order of weight:

1. **The error mapper is the product.** Exit 1 vs 2 hinges on
   distinguishing SQLITE_CONSTRAINT-family results from busy/corrupt (§6.1,
   §16 verification item). That is bespoke code against the driver's error
   types either way; sqlc generates none of it.
2. **The hard SQL is unrepresentable in sqlc anyway**: the dump serializer
   (hand-rolled by contract, §8.1), the whitelist load parser, PRAGMA
   choreography per connection (§3.1), `verify`'s R-rules, and the
   trigger-heavy DDL live outside any query generator. What remains for
   sqlc is ~dozens of one-table CRUD statements — the part that costs
   nothing to write by hand.
3. Trigger-raised errors (`RAISE(ABORT, 'illegal status transition …')`)
   surface as plain driver errors; sqlc's type layer adds no safety there,
   and its analyzer does not model triggers.
4. One fewer codegen step + binary pin in a project whose CI already builds
   red fixtures, fuzzers, and a determinism matrix.

Shape: `internal/db` owns `Open(path, mode)` (DSN pragma assembly for
read/write connections), `ErrClass(err)` (the single 0/1/2 mapper), and tiny
typed row structs with explicit `Scan` targets; all RETURNING statements go
through `QueryRow` per spec §3.1. If the query surface ever grows
(FTS5-backed `search`, `stats` — §17 deferrals), sqlc v1.31+ is a viable
revisit, and this document records that its SQLite dialect is no longer the
blocker it was pre-v1.18.

Migrations: **none in v0 — and no goose.** Schema v1 is a single compiled-in
canonical DDL, `user_version`-stamped (§3.1, §8.5 byte-equality check);
future schema versions arrive as compiled-in DDL + stepwise in-Go upgrade
functions gated on `user_version`, which a migration library would only
obscure (the dump loader must know every canonical DDL byte-exactly anyway).

## 7. Architecture / package layout

**Facts:** the official guidance (<https://go.dev/doc/modules/layout>) and
current community consensus for CLIs: thin `cmd/<binary>/main.go`, all real
code under `internal/`, packages by domain responsibility, **flat until
proven otherwise**; no `pkg/`, no hexagonal ceremony for a tool with one
storage engine and one delivery mechanism. Hexagonal/ports-and-adapters buys
swappable infrastructure — selftracked's storage engine is a spec-level
axiom (§1, §3), so the abstraction would model a change the thesis forbids.

**Verdict — concrete layout (flat, one package per spec concern):**

```
cmd/selftracked/main.go   thin: os.Exit(cli.Run(os.Args, os.Stdout, os.Stderr))
internal/cli/             verb registry, per-verb FlagSets, JSON envelope,
                          exit-code mapping (the only place os.Exit codes exist)
internal/verbs/           one file per verb family: task.go, epic.go, story.go,
                          worklog.go, link.go, paths.go, config.go, importer.go,
                          verify.go, prime.go, gate.go …
internal/db/              Open (DSN pragmas, read vs EXCLUSIVE-write), tx helper,
                          error classifier (constraint vs busy vs corrupt)
internal/schema/          embedded canonical DDL per schema version, gates,
                          user_version/application_id constants
internal/dump/            deterministic serializer + whitelist load parser
                          (§8.5) — fuzz targets live here; no imports from verbs
internal/verify/          R1–R15 rules, each with its red fixture
internal/refs/            §4 reference grammar: parse/format `#NN`,
                          `epic:SLUG/SID`, `CLASS@SCOPE:RELPATH`
internal/staterender/     STATE.md + prime JSON rendering (shared ordering rules)
internal/scaffold/        init: embedded hook scripts, PROMPT.md, AGENTS.md,
                          .claude/ files, gitignore entries
internal/gitx/            thin exec-git helpers: cat-file, mv, diff-names
```

Dependency direction: `cli → verbs → {db, schema, refs, dump, verify,
staterender, gitx}`; `dump` and `schema` import nothing above stdlib+driver
(they are the security/determinism kernel and the easiest to fuzz/test in
isolation). No interfaces until a second implementation exists; the repo
layer is concrete functions taking `*sql.Tx`.

## 8. Task runner

**Facts:** candidates — GNU make (ubiquitous, already on every POSIX dev
box and CI runner), Taskfile/go-task (extra binary install, YAML), mage
(Go-code build files, `go run` bootstrap). The project's own generated hooks
are deliberately POSIX sh (§9); CI is GitHub Actions with a Windows leg for
dump determinism only.

**Verdict: Makefile.** Zero new tooling for contributors and CI; targets are
one-liners around the Go toolchain, which is exactly the case where make's
weaknesses (deps tracking, portability of complex recipes) never appear —
and where Taskfile/mage add an install step for no capability. Sketch:

```make
GOLANGCI_VERSION := v2.12.2
BIN := ./bin

.PHONY: build test lint fix fmt fuzz vuln verify-fixtures ci

build:            ## static binary, reproducible flags
	CGO_ENABLED=0 go build -trimpath -ldflags='-s -w -buildid=' -o $(BIN)/selftracked ./cmd/selftracked

test:
	CGO_ENABLED=0 go test -race -shuffle=on ./...

lint: $(BIN)/golangci-lint
	$(BIN)/golangci-lint run

$(BIN)/golangci-lint:
	curl -sSfL https://raw.githubusercontent.com/golangci/golangci-lint/HEAD/install.sh \
	  | sh -s -- -b $(BIN) $(GOLANGCI_VERSION)

fix:              ## modernizer gate — fails on exit status OR non-empty diff output
	@out="$$(go fix -diff ./... 2>&1)" || { printf '%s\n' "$$out" >&2; exit 1; }
	@[ -z "$$out" ] || { printf '%s\n' "$$out" >&2; exit 1; }
	# corrected after round-5 verification: the earlier guard captured only
	# stdout and discarded exit status, so a broken .go file (go fix exits 1,
	# empty stdout, error on stderr) made this target pass silently; now both
	# the exit status (verified-but-undocumented on go1.26.4) and output
	# emptiness (documented) are checked. `go fix ./...` locally to apply

fmt:
	$(BIN)/golangci-lint fmt

fuzz:             ## the load-parser is the security boundary (§8.5/§16)
	go test -run=^$$ -fuzz=FuzzLoadParser -fuzztime=60s ./internal/dump

vuln:
	go tool govulncheck ./...

ci: lint fix test vuln build
```

(`-race` in CI is the one target where CGO is permitted — the race runtime
needs it on some platforms; the shipped artifact is always the
`CGO_ENABLED=0` build.)

## 9. Everything else a 2026 Go CLI should adopt

- **govulncheck in CI** — `golang.org/x/vuln` **v1.6.0** (2026-07-09),
  pinned via the go.mod `tool` directive (Go 1.24+), run as `go tool
  govulncheck ./...`. Source: <https://pkg.go.dev/golang.org/x/vuln>
- **Reproducible builds now, not later**: `CGO_ENABLED=0`, `-trimpath`,
  `-ldflags=-buildid=`; verify in CI that two consecutive builds are
  byte-identical (cheap, and the project's whole ethos is deterministic
  bytes). `GOFLAGS=-trimpath` in CI env keeps `go test` binaries consistent
  too.
- **goreleaser v2.17.0** (2026-07-04) — *deferred until distribution
  becomes a deliverable*; when adopted it provides the `strk` second binary
  name, archives, and checksums. Not a v0 dependency. Source:
  <https://github.com/goreleaser/goreleaser/releases>
- **testscript** (`github.com/rogpeppe/go-internal/testscript`) **v1.15.0**
  (2026-04-17) — the highest-leverage addition: txtar-scripted end-to-end
  verb tests asserting stdout JSON, stderr, and **exit codes** (`! exec`,
  `[exit:1]`-style patterns), with `go test` coverage integration. The
  spec's exit-code contract and refusal messages (§6.3 examples) translate
  almost line-for-line into testscript scripts; red fixtures for every
  R-rule (§16) become txtar files. Source:
  <https://pkg.go.dev/github.com/rogpeppe/go-internal>
- **Native fuzzing** for the dump whitelist parser (§8.5 mandates it) and
  the refs grammar parser; corpus committed under `testdata/`.
- **CI matrix** per §16: ubuntu + macos + windows for dump
  byte-determinism; hooks exercised on POSIX runners; `go vet` is implied by
  `go test` but run explicitly with the full flag set anyway.

### Proposed go.mod + tool versions

```
module <module-path>            // decided at repo publication

go 1.25.0
toolchain go1.26.5

require (
    github.com/rogpeppe/go-internal v1.15.0 // test-only: testscript
    modernc.org/sqlite v1.54.0
)

require modernc.org/libc v1.74.1 // indirect — MUST track the driver's own
                                 // go.mod pin exactly (fragile-dep notice)

require golang.org/x/vuln v1.6.0 // tool-only: govulncheck (matches the
                                 // tool directive below)

tool golang.org/x/vuln/cmd/govulncheck
```

Note: `go mod tidy` regenerates the `// indirect` comment slot on that libc
line (it is tooling-owned, not hand-authored), so the actual pin-discipline
enforcement cannot live in the comment text — it lives in the Makefile/CI
check that compares the resolved `modernc.org/libc` version against the
driver's own go.mod requirement.

Companion pins outside go.mod: `GOLANGCI_VERSION := v2.12.2` in the
Makefile (binary install — the project advises against `go install`);
goreleaser v2.17.0 recorded above but not yet a dependency. Licensing note
for §16: modernc.org/sqlite and modernc.org/libc are BSD-3-Clause —
Apache-2.0-compatible; record both in NOTICE at dependency intake.

### Surprises vs conventional wisdom

1. **`modernize` is no longer a gopls side-tool** — Go 1.26 rebuilt `go
   fix` as the modernizers' home with a `-diff` CI mode; pinning the old
   gopls-internal runner would be building on a superseded path.
2. **No CLI framework wins on this spec's own terms** — with a closed verb
   set, JSON-only errors and a strict exit-code contract, every framework is
   configuration spent silencing behavior the spec forbids; stdlib dispatch
   is smaller than the silencing code.
3. **sqlc's SQLite story is genuinely fixed** (STRICT since v1.18,
   RETURNING expansion and a DB analyzer in v1.31) — it is rejected here not
   for immaturity but because this project's hard SQL (serializer, load
   parser, pragma choreography, error classing) sits entirely outside what
   any query generator covers.
4. **The libc pin is a real constraint, not pedantry** — the driver's docs
   mandate exact-version agreement with `modernc.org/libc` (v1.74.1 for
   v1.54.0); a casual `go get -u` can silently break the storage engine, so
   dependency updates of the driver pair are a single reviewed commit.
